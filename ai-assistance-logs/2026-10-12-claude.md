## 1. User request

QDVC Response Letter is a macOS (Swift) application that helps an author write a typical response letter for a journal paper resubmission.

As you may be aware, when you send in a journal paper and you're granted a revision, you get a decision letter (for the purposes of this app, assume it is formatted as plain text) which typically contains comments from a combination of [senior editor AND/OR associate editor AND/OR special issue editor AND/OR department editor AND/OR track chair] and then the comments from the reviewers (reviewer 1, reviewer 2, reviewer 3, etc.)

It is then necessary to write a response letter responding to each of the comments, one at a time. It is at the author's discretion how the comments are itemised. Once they are itemised, they are typically given ID numbers (e.g., SE-01, SE-02, SE-03; AE-01, AE-02, AE-03; RE1-01, RE1-02, RE1-03; etc.) and the author needs to write a response each of them.

The app should enable the user to:

* Create a new response document, starting by pasting the decision letter.
* Deconstruct the response document into appropriate 'comments' by highlighting the comment text, then enumerating all the demarcated comments.
* Triage the comments by marking each comment in a colour (typically green = easy to address, yellow = a little bit trickier, red = requires thorough consideration, needs in-depth discussion with coauthors) and entering dot-points of the initial ideas for a response.
* Tag comments as being related (e.g., comment AE-03 is summarising RE1-07 and RE2-05).
* Draft comment responses. Each response may contain:
   * Free-flowing text
   * A text label which is re-used across multiple comments (e.g., a page reference, section reference, verbatim quote, number of data points, etc.). These are "text labels" in that there is one central/official version of the string, to which all instances are just like pointers. The user should be able to see the list of all of these and make changes that cascade to all instances. (Please help me come up with a better terminology for this concept...)
   * A reference to another comment (e.g., as in "see also our response to comment `AE-07` and `RE1-03`"). This is a similar concept to above "text labels", but specifically accommodates for the comments structure of a response letter itself, which may sometimes be renumbered (more on that in a moment).
* Export a DOCX for the response letter, which is an A4 document with a very long multi-page table with columns (ID, Editor/Reviewer Comments, Response). Note that "ID" is not displayed in the header, just leave that column header blank. At the start of a section of comments, create a blank row with a black background and bold white text in the second column like "Senior Editor comments", "Reviewer 1 comments", etc.

An important - but relatively complicated - feature is the ability to split a comment into two, or merge two adjacent comments together. This results in a renumbering of comments, which the app should just gracefully handle. It may also result in inconsistencies, especially when splitting. For example if there were several other comments referencing SE-05, and that has now split into SE-05 and SE-06, then the app must require the user to clarify — for each of the original references to SE-05 — whether it should now point to SE-05 or SE-06. There may be other complications similar to this.

This app belongs to the Mac family in the QDVC suite of apps. See "Native macOS applications (Swift)" heading in https://github.com/qdvc-apps/. ## 6. LLM response

Two different causes. The first is an error: the core library's public structs got Swift's automatic initialisers, which are `internal`, so the app module can't call them. The second is a concurrency warning: `MainActor.assumeIsolated` was returning a non-Sendable `NSAttributedString` from a context that was already on the main actor. I'll fix both, and check the core for any other public types with the same initialiser problem.

Both problems are fixed in **qdvc-response-letter-mac.zip**. The core tests still pass, but I still can't build the app itself here.

**The `Renumbering` error.** Swift gives a struct an automatic initialiser, but it is always `internal`, so the app couldn't create one from outside the core library. I added public initialisers to `Renumbering` and to the other public result types (`PendingReference`, `SplitResult`, `MergeResult`, `Issue`, `LoadedWorkspace`, `FileStamp`, `ResponseLetter.Progress`). To head off more of the same, I scripted two checks:
- Every public struct the app might construct now has a public initialiser.
- All 127 core properties and methods the app uses are public.

**The `NSAttributedString` warning.** `EditorTextView` is a text view, so it already runs on the main thread. Wrapping calls in `MainActor.assumeIsolated` was unnecessary, and passing a non-thread-safe value out of that wrapper is what Swift 6 objects to. I removed every such wrapper in the text views.

There were also two places where the same kind of problem would probably have surfaced later:
- The paragraph-style helper is now callable from the text-storage callback, which isn't tied to the main thread.
- The Variable and Cross-reference pill objects are now always created on the main thread.

The only wrappers left are the undo handler and the pill's lookup of its label, which return only plain values, so they shouldn't trigger the warning.

If there are many more errors, `scripts/build-app.sh 2>&1 | grep -E "error:" | sort -u` will collect them all at once. Warnings can wait unless they look suspicious.
